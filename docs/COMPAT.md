# Plugin compatibility

`tmux-agent-wizard` runs herdr plugins largely unmodified: same `herdr-plugin.toml`
manifest format, same trust-preview install gate, same `HERDR_*` environment
contract for the parts of it tmux can support. See
`third_party/herdr/reference/plugins.mdx` for the
herdr side of this contract, and `src/plugin/` for the implementation.
`taw plugin install|update|action invoke|pane open` are `taw` CLI verbs over that
library; see `taw plugin --help` for the full command tree. Each commit of a GitHub
plugin lives in a folder of its own, `plugins/github/<owner>/<repo>@<12-char sha>`
under taw's state folder, and the registry's record names it; a built tree is never
moved, so a build that writes its own absolute path keeps a path that exists. `taw
plugin update [id|source...] [--yes]` asks the remote for each GitHub-installed
plugin's commit at its recorded ref, and fetches only when it is not the one installed,
into the new commit's folder beside the old one. It runs the same trust gate as
`install` and the build there, and only then switches the records, in one write, and
removes the old folder; a decline or a failed fetch or build removes the new folder and
leaves the installed copy untouched, and a folder left by Ctrl-C at the prompt (or by a
run that was killed) is removed at the next install or update of that repository, with
the records and the live folder untouched. A build only ever runs in a folder that run
made: `install` over an installed plugin at the commit it has, and an update to a commit
whose folder another record lives in, build in `<repo>@<12-char sha>-<n>` (the smallest
`n` from 2 up that is free), and which folder a record points at is decided by file
identity, so `Owner/repo` and `owner/repo` are one folder on a case-insensitive disk.
Plugins that share one checkout (installs from an older taw) update together. `@<sha>`
(and `--ref <sha>`) take a full 40-character commit and pin the plugin to it, and an
update of a pinned plugin whose folder is present is unchanged with nothing asked of
GitHub; a ref that looks like a short commit (7 to 39 hex characters) and that the remote
does not name is refused before any fetch with "give the full 40-character commit, or a
branch or tag". GitHub serves a commit of any fork of a repository under that
repository's address, so a pin should be a commit you have looked at; the trust preview
names the commit it fetched. A process a plugin started from its old folder keeps running
from it after an update (restart it, or run `taw plugin startup` once it has stopped).
Two `taw plugin install` or `update` runs of one repository at the same time are not
supported: run one at a time (there is no lock). A linked plugin is left alone, no
startup commands run, and the command exits 1 when any plugin failed, with every plugin
still listed.

## The environment contract

Every plugin process (`[[build]]`, `[[startup]]`, an invoked action, a pane
command, a matching `[[events]]` hook) is launched with a working directory of the
plugin's own root and an environment built by `src/plugin/env.rs`. Each variable
below is set as both its herdr name and a `TAW_` twin with the same value (e.g.
`HERDR_BIN_PATH` and `TAW_BIN_PATH`).

| Variable | Set by taw? | Notes |
|---|---|---|
| `HERDR_BIN_PATH` | yes | absolute path to the running `taw` binary, the portable way for a plugin to call back in, instead of a hardcoded `herdr`/`taw` on `PATH` |
| `HERDR_ENV` | yes | always `1` |
| `HERDR_PLUGIN_ID` | yes | |
| `HERDR_PLUGIN_ROOT` | yes | the installed/linked plugin directory |
| `HERDR_PLUGIN_CONFIG_DIR` | yes | `<config>/plugins/<id>`, created on demand |
| `HERDR_PLUGIN_STATE_DIR` | yes | `<state>/plugins/state/<id>`, created on demand |
| `HERDR_PLUGIN_CONTEXT_JSON` | yes | herdr's flat `PluginInvocationContext` fields (`workspace_id`, `tab_id`, `focused_pane_id`, `focused_pane_cwd`, `focused_pane_agent`, `focused_pane_status`, `workspace_cwd`, `workspace_label`, `tab_label`, `worktree`, `selected_text`, `clicked_url`, `link_handler_id`, `invocation_source`, `correlation_id`; `null` where taw has nothing, which is always so for the last six), and taw's own nested `{"workspace":…,"tab":…,"pane":…,"caller_pane_id":…}` beside them, plus any extra top-level fields the caller merges in (e.g. a worktree record); the fields of a pane's invocation are that pane's, its tab's and its workspace's |
| `HERDR_PLUGIN_EVENT` | yes | `"startup"` for startup hooks, `"action"` for action invocations and plugin-pane opens, or the event name (e.g. `"pane.agent_status_changed"`) for event hooks |
| `HERDR_WORKSPACE_ID` / `HERDR_TAB_ID` / `HERDR_PANE_ID` | yes, when present | an action or pane opened with `--pane` has that pane's id and the ids of the tab and workspace it is in; with `--tab`, that tab's and its workspace's; with `--workspace`, that workspace's; an action invoked without `--pane` has the pane in front, as in herdr: the active pane of `--tab` or `--workspace`, else the pane the command runs in, else the active pane of tmux's current session |
| `HERDR_SOCKET_PATH` | **never** | see below |
| `HERDR_PLUGIN_ACTION_ID` | **no** | herdr sets this on action commands specifically; `taw` folds every invocation into the same `HERDR_PLUGIN_EVENT`/`HERDR_PLUGIN_CONTEXT_JSON` pair instead |
| `HERDR_PLUGIN_EVENT_JSON` | yes, on event hooks | herdr's event envelope, `{"event": "worktree_created", "data": {"type": "worktree_created", ...}}`, with the fields herdr's event has (`null` where taw has nothing). A worktree event's `data.worktree` has herdr's `WorktreeInfo` fields and `data.workspace.worktree` its `WorkspaceWorktreeInfo` (`checkout_path`, `repo_root`, `repo_name`, `repo_key`, `is_linked_worktree`). `taw`'s own events (`agent.done` and the rest) carry their payload under `data`, with the kind in herdr's spelling |
| `HERDR_PLUGIN_ENTRYPOINT_ID` | **no** | herdr sets this on pane commands to identify which `[[panes]]` entrypoint launched them |
| `HERDR_PLUGIN_CLICKED_URL` / `HERDR_PLUGIN_LINK_HANDLER_ID` | **no** | see "Link handlers" below |

### `HERDR_SOCKET_PATH` is never set

herdr's socket is its live JSON-RPC control channel; `taw` has no daemon and no
socket, so there is nothing to point this at. It is not just omitted: `taw`
actively strips `HERDR_SOCKET_PATH`/`TAW_SOCKET_PATH` from its *own* inherited
environment before running a plugin's build commands, so a `taw` invoked from
inside a real herdr session never leaks herdr's live socket path to a plugin
process it launches. A plugin that talks to the raw socket transport directly
(rather than going through `HERDR_BIN_PATH`) cannot work here at all; that is the
single largest compatibility gap, and it is deliberate: plugins that talk
raw JSON-RPC are unsupported.

### `PATH` in the panes

Separately from herdr's variables, the plugin puts `taw` on `PATH`: tmux's global environment `PATH`
gets, in front, `bin` in taw's state folder (`$TAW_STATE_DIR`, else `$XDG_STATE_HOME/tmux-agent-wizard`,
else `~/.local/state/tmux-agent-wizard`), a folder that holds only a `taw` link to the binary the plugin
resolved, so it can never shadow another program. Panes created from then on have it; existing panes
keep their `PATH`. A reload does not add the folder twice and moves the link to the binary resolved
then. `@agent-wizard-path off` (default `on`) and a reload takes the folder back out and leaves every
other entry as it was. tmux gives a pane the `PATH` of the command's client when that client is not
attached to a session, so a pane that a script outside tmux creates has that script's `PATH`, and so do
the first pane of a session started from a terminal and a window that a `tmux new-window` typed in a pane
opened before the load makes. A macOS login shell's `path_helper` keeps the folder but moves it behind the
system folders, so a `taw` in `/usr/local/bin` wins there. A session `PATH` (a user's `update-environment`
holding `PATH`) wins over the global one for panes made with keys.

### The pane environment `@agent-wizard-herdr-env` gives

The table above is about the processes taw launches for a plugin. Separately, the tmux option
`@agent-wizard-herdr-env` (off unless `on`) puts herdr's environment into tmux's global
environment, so a program that follows herdr's guide for agents (Command Code, Crush, Kiro CLI,
Muse Code, Prime Agent: report only where `HERDR_ENV=1`, `HERDR_PANE_ID` and `HERDR_BIN_PATH`
are set) reports to taw from any pane created afterwards. The plugin sets three values when it
loads, and removes them on a reload with the option off while `HERDR_PANE_ID` is still its own
word:

| Variable | Value | Notes |
|---|---|---|
| `HERDR_ENV` | `1` | |
| `HERDR_BIN_PATH` | the `taw` binary the plugin runs, absolute | herdr's agents run `"$HERDR_BIN_PATH" pane report-agent ...`, `report-agent-session` and `release-agent`, which take herdr's arguments, and since the resume command `-- <command>` too |
| `HERDR_PANE_ID` | `%calling` | tmux gives every pane the one global value, so this is a fixed word: taw's pane verbs read it as the pane the process runs in (`$TMUX_PANE`), with or without the option, and fail with `no current pane` when `$TMUX_PANE` is not set |

`HERDR_SOCKET_PATH` is not set (taw has no socket), so an agent that reports through the socket
reports nothing. An agent that also requires `HERDR_SOCKET_PATH` (herdr's guide lists it among
the variables) reports nothing either. Nothing of this reaches a plugin process or a `[hooks]`
command: a plugin's action, startup or event hook, its build steps and its pane and popup
entrypoints get the table above, and `HERDR_PANE_ID`, `HERDR_TAB_ID`, `HERDR_WORKSPACE_ID` and
their `TAW_` twins come from the invocation's context only, so a startup hook has none and an action or pane opened with
`--pane` has that pane's real id (a pane or popup tmux starts is run behind an `env -u` for the
names its context does not set). A hook names its pane in `TAW_PANE`.

### Link handlers parse but do not dispatch

`herdr-plugin.toml`'s `[[link_handlers]]` table is parsed (`src/plugin/manifest.rs`)
so a manifest that declares one still loads, but nothing in `taw` currently routes a
clicked terminal URL to a handler action; that would require intercepting a
modified mouse click on pane content, which tmux's own mouse mode does not expose
to a plugin the way herdr's own renderer does. `HERDR_PLUGIN_CLICKED_URL` and
`HERDR_PLUGIN_LINK_HANDLER_ID` are therefore never set, because the event that
would set them never fires.

### `herdr api snapshot` and `herdr api schema` are not answered

herdr's `api snapshot` prints the whole session as one record: workspaces, tabs, panes, agents and
a layout record for every tab with the rectangle of each pane and each split. taw has the lists
(`workspace list`, `tab list`, `pane list`, `agent list`) and a split tree per tab (`layout export`),
but not the rectangles, so `taw api snapshot` and `taw api schema` do not exist and a plugin that
runs them (`herdr-resurrect` does) fails. `taw session save` and `taw session restore` do that job
for tmux: they keep each window, pane, folder and agent session and bring them back.

## Compatibility matrix

The plugins below were installed with `taw plugin install owner/repo` and tried on 2026-10-27 on
Ubuntu with tmux 3.6, the first ten rows. A row says what happens under taw after the fixes that
trial led to. Plugin support is in beta: these ten are the only plugins run under taw so far.

| Plugin | Uses | Status | Why |
|---|---|---|---|
| `herdr-automatic-rename` (`qu8n`) | startup, event hooks, `workspace`/`tab` renames | works, with a note | it needs `jq`. It names tabs `[N] <program>` as it does under herdr. It also numbers workspaces, and a workspace is a tmux session here, so your sessions become `[1] main`: a script or `tmux attach -t main` that names the session no longer matches |
| `dev-layout-bootstrap` (`ogulcancelik/herdr-plugin-examples`) | action, `pane`/`tab` verbs | works | needs `lua`; the action made the three panes its README describes |
| `herdr-worktree-setup` (`tdi`) | build (`npm ci`), `worktree.created` event | works | needs `node` and `npm` for its build; its `[default] steps` ran in the new worktree |
| `github-link-preview` (`ogulcancelik/herdr-plugin-examples`) | link handler, `plugin pane open` | does not work for its purpose | it is opened by a click on a link, and tmux does not hand a click on a URL to a plugin (see "Link handlers parse but do not dispatch"). Its action and its `plugin pane open --plugin ... --entrypoint ... --placement ... --direction ... --env ... --focus` call work; only the click on a link cannot reach it in tmux |
| `herdr-reviewr` (`persiyanov`) | actions, `pane process-info`, panes, event hooks | works | its `open` action (`taw plugin action invoke open --plugin persiyanov.reviewr`, from the pane you are in or with `--pane`) opens its pane beside that pane; the pane shows the repo's uncommitted changes, its keys work, and `q` or its `close` action closes it. | `herdr-auto-title` (`kryptamine`) | herdr's socket API | does not work | it stops at once with "HERDR_SOCKET_PATH is not set": it talks to herdr's socket, which tmux does not have. It also needs `go` for its build |

| `herdr-browser` | browser content drawn inside a pane | ✗ | it was written for herdr's `pane.graphics.*` methods, which herdr removed in 0.9.2; herdr now renders the standard Kitty graphics an app prints, and tmux draws none in a pane (see `docs/PARITY.md` "Kitty graphics in a pane"); not degraded, unsupported |

"expected / untested" means: the plugin's declared needs (actions, event hooks,
overlay/split panes, `HERDR_BIN_PATH` CLI calls) all map onto something `taw`
implements or specifies, but no automated or manual test in this repository has
actually installed and run these specific third-party plugins. Re-classify a row
once someone does.

## Events

All 19 of herdr's event names fire (`third_party/herdr/reference/event-names.txt`
is the list; `matching_events` in `src/plugin/manifest.rs` is what matches an
`on = …` against them). A hook receives `HERDR_PLUGIN_EVENT` set to the name and
`HERDR_PLUGIN_CONTEXT_JSON` holding whichever of `workspace`/`tab`/`pane` the event
is about, in the same record shapes the CLI returns.

There is no streaming equivalent: herdr's `events.subscribe`/`events.wait` need a
live socket, and a hook process launch is what replaces them here (see
`docs/PARITY.md` "Structural gaps"). An event is therefore delivered once, detached,
with no ordering guarantee against another plugin's hook for the same event.

| Event | Fired by |
|---|---|
| `pane.agent_status_changed` | the `pipe-pane` watcher, on every state transition it records: the event every other agent-facing one builds on (see `docs/ARCHITECTURE.md` "Watcher lifecycle") |
| `pane.created` | tmux's `after-split-window` hook (`#{pane_id}` is the new pane), whether the split came from `taw pane split` or a key; the verb itself emits nothing, so a pane is reported exactly once, and when the event is built the verb answers with the pane record it carries |
| `pane.closed` | tmux's `after-kill-pane` and `window-unlinked` hooks, diffing a pane roster kept in `@agent_wizard_panes`; tmux names no killed pane in any hook, so the id is recovered by comparing the roster with `list-panes -a`. Covers `taw pane close` and a hand `prefix + x` alike, once each. A process exiting is `pane.exited`, not a close (herdr keeps the two apart), and the roster cannot tell the two apart, since a pane that exited is gone from `list-panes` as a killed one is. So the `pane-exited` hook marks the pane in `@agent_wizard_exited` with tmux commands of its own, ahead of the job that fires `pane.exited`, and every detection leaves a marked pane out of what it reports. A detection reads the marks right after it lists the live panes, in the same tmux call: tmux runs the commands of a hook like `pane-exited` and `window-unlinked` from the server's own queue in the pass of its loop that sees the event, before any client's commands (3.2 and 3.6b alike), so a command that finds the pane gone finds its mark. Whoever drops a pane from the roster takes its mark off, and the marks are the last 400 characters at most. The exit's own take of the roster is a detection as well, so a pane killed in the same moment as another exits is reported by it, once. The marks keep the guarantee only while tmux's command queue is not blocked: a hook of your own that blocks tmux's command queue (a `run-shell` without `-b`, or an `if-shell` without `-F`, on any hook) holds the mark's command back behind it until it ends, for tmux runs nothing that is queued after a command that waits. A source of the plugin over itself (an upgrade of taw, a reload of tmux.conf) puts its new hook entries in before it takes the old ones off, so that a hook is never without one: an event in the moment between runs both, a duplicate where the other way lost it. The roster is written by a compare-and-set on a count of its writes, kept beside it in `@agent_wizard_panes_generation`: a writer reads the roster and the count, then the live panes, and its write lands only if the count is still what it read, else it reads again (at most 20 times). So a detection that read the panes before a pane's exit was handled cannot write them back over what that exit did, and two detections that overlap report one close once |
| `pane.exited` | the pane's process exiting while the pane itself stays (tmux `remain-on-exit`), from the same hook |
| `pane.focused` | tmux's `after-select-pane` hook |
| `pane.updated` | a pane's title, command, or reported agent metadata changing, as the watcher notices it |
| `tab.created` | tmux's `window-linked` hook (`#{hook_window}`/`#{hook_session}`), for `taw tab create` and a hand `prefix + c` alike, one event per window. When the event is built (a plugin or a `[hooks]` command listens for it), `taw tab create` answers with the records it carries, so the two are one read: the new window's name, which tmux's automatic-rename changes as its shell starts, is the same in both |
| `tab.closed` | `taw tab close`, and tmux's `window-unlinked` hook |
| `tab.focused` | tmux's `session-window-changed` hook |
| `tab.renamed` | `taw tab rename`, and tmux's `after-rename-window` hook |
| `workspace.created` | tmux's `session-created` hook (`#{hook_session}`), for `taw workspace create`, `taw worktree create` and a hand `tmux new-session` alike, one event per session. When the event is built, `taw workspace create` answers with the records it carries, as `taw tab create` does with `tab.created`, except that the workspace's `focused` is read again after the verb has moved a client onto it (the hook can read the session before the move, when no client is on it, and the event says what it read) |
| `workspace.closed` | `taw workspace close`, and tmux's `session-closed` hook. Each session closed is one event, so `taw workspace close --group` reports the workspace and each worktree workspace it closed |
| `workspace.focused` | tmux's `client-session-changed` hook (which is what fires when any client switches session, however it was asked to) |
| `workspace.renamed` | `taw workspace rename`, and tmux's `after-rename-session` hook |
| `workspace.updated` | a workspace gaining or changing worktree provenance, or its metadata being reported (`taw workspace report-metadata`) |
| `worktree.created` | `taw worktree create` (alongside `workspace.created`, `tab.created`, `pane.created`) |
| `worktree.opened` | `taw worktree open`, whether or not it had to create the session |
| `worktree.removed` | `taw worktree remove` (plus `workspace.closed` when the linked session was still open) |
| `layout.updated` | tmux's `window-layout-changed` hook, which fires for `taw layout apply`/`set-split-ratio`, `taw pane resize`/`swap`/`move`/`zoom`, and any resize or split done by hand |

`taw plugin event <name>` fires one event at every plugin that hooks it, which is how to
test a hook without waiting for the thing that normally triggers it. It fires the `[hooks]`
commands of that event too, and `taw hooks test <event>` is the way to try only those.

Hook-sourced payload fields are expanded through tmux's `#{q:…}` quoting (available since
tmux 3.1, below this plugin's 3.2 floor), so a session id such as `$3` or a window name
containing `$(…)` reaches the plugin intact instead of being expanded by the hook's shell.

The popup itself is gated the same way: `display-popup -B` (a frameless full-size
popup) is used on tmux ≥ 3.3; below that the popup keeps its frame and title.

## Hooks from the config

`[hooks]` in `config.toml` hears the same 19 events as a plugin, from the same code: a
command hooked to `tab.created` runs at the moment a plugin's `[[events]] on = "tab.created"`
does. It is told the event as `TAW_*` environment variables and, on standard input, as the
context a plugin gets in `HERDR_PLUGIN_CONTEXT_JSON` with `"event"` added. Nothing about the
plugin contract changes: a plugin keeps its own environment, log and manifest, and a `[hooks]`
command has none of them. A `[hooks]` command does get the environment tmux would give a new
pane of the session the event is about (the session's own over tmux's global environment, and
what either removes taken out) and `TMUX` beside the `TAW_*` variables, whichever process fired
the event, the watcher included; an event about no session, or one that is gone, has the global
environment alone. The README's "Hooks" section is the reference for the variables, the time
limit and the log.

Names that are not in `event-names.txt` and are taw's own:

| Name | Fires |
|---|---|
| `agent.blocked`, `agent.working`, `agent.idle`, `agent.done` | with `pane.agent_status_changed`, when the agent goes into that state. Only a change of state is one: a new agent in the same state, an agent leaving its pane and a change into `unknown` fire the status event alone. An agent whose process ends while it is working or blocked has its turn ended first, so `agent.done` (`agent.idle` for a pane being looked at) fires before it leaves; and an agent that only its launch hint names, read as `unknown` for a moment, fires the agent event of the state it comes back to |
| `sandbox.started`, `sandbox.stopped` | when the pane's watcher records that the agent in front of a pane runs in a container (`@agent_container` set) and when that container has left the pane (`@agent_container` taken off) or the pane has gone with it still in front (closed, or its tmux server ended), for a container `taw sandbox` started and for one typed by hand. The event's own `sandbox` field is `{"profile", "runtime"}`, what came or what left; `agent` is the agent in it. `TAW_SANDBOX` and `TAW_RUNTIME` say the two, here from the event's own field and on every other event about a pane in a sandbox from the pane's record, a `notification` and an `agent.done` included. A watcher started again announces no container that was already there, and a runtime that changes between two reads is a stop and then a start. Hooks only: no plugin event fires |
| `notification` | where taw shows a toast, so after the toast's delay and never for a pane you are looking at. `TAW_KIND` is `request` or `done` and `TAW_MESSAGE` is the toast's words on one plain line. `taw notification show` fires it too, with no pane, when no app holds the lease on that machine; under a fresh lease the app on the Mac that holds it makes the sound and runs the hook instead, with `TAW_MACHINE` set to that machine's name |

An agent whose integration reports its own state (`kilo`, `kimi`, `mastracode`, `omp`, `opencode`,
`pi`) fires these for what it reports, as any agent does for a change of state: `taw pane
report-agent` writes the state and nudges the pane's watcher, which takes the report in within a
moment, though the pane prints nothing, and announces the change, once, with the status event, the
`agent.*` event and the `notification` for the toast it earns. A turn shorter than one tick of the
watcher, `working` and then `idle` reported back to back, is announced as its start and its end,
from a stamp `taw pane report-agent` leaves on the pane. The same report again fires nothing. An
`idle` that ends a turn for a pane that is not being looked at is `done`, and stays `done` when
`idle` is reported again. Its end is announced too: when the pane's own shell is back at its prompt
and the last state taw had heard was `working` or `blocked`, the watcher writes the turn's end
(`idle` for a pane being looked at, `done` otherwise) as it does for any agent that exits, so the
status event, `agent.done` (`agent.idle` for a pane being looked at) and the done `notification`
fire once, and letting the pane go a read later is the status event alone. Watchers started by an
older taw announce no reports until they are started again: `taw watch status` marks them, and
`taw watch attach-all --restart`, run with the taw that is installed, starts each of them again.

Two more keys are not events. `pre_close` is asked before taw closes a session, a window or a
pane (`taw workspace close`, `tab close`, `pane close`, and the popup's `x`), and
`pre_worktree_remove` before it removes a worktree (`taw worktree remove`, and the popup's
`x` on a closed worktree). taw waits for them, and a non-zero exit refuses. A refusal is the
error code `hook_refused`, the one `taw session open` already reports for a create hook: the
message names the hook and carries what it wrote to stderr (the last 16 KiB at most), and
nothing is closed or removed. A hook that runs past `[sessions] hook_timeout_seconds` refuses
too, and `0` there means no limit here as it does for the create hooks, so a hook that never
ends holds the close. `workspace close --group` asks about every session in the group before
it closes any, and so does the popup's `Close them too?` answered with `y` (`x` on a session
with worktree sessions open, or on the last pane of its last window, since that closes the

## Machines

`taw app` and the `machine` verbs list the machines under `[machines]` (one `name = "ssh destination"` per line, or `[machines.name]` with `ssh` and `taw`) and go in to them, all over ssh. With no `[machines]` taw behaves as it always did. README's "Remote machines" is the guide; this is the contract.

| Verb | Envelope | Shape |
|---|---|---|
| `taw app [--go <target>]` | none | a screen, so a person's terminal only: it prints no envelope. `--go` opens on `last`, a pane of this machine as in `%7`, or `<machine>:<id>` as in `studio:%16` |
| `taw machine list` | `cli:machine:list` | `result.machines`: for each machine `name`, `destination`, `taw`, `live`, `last_seen`, `taw_version`, `protocol` and `words`, as the app last heard (no ssh) |
| `taw machine add <name> <ssh-host> [--taw <path>]` | `cli:machine:add` | writes the machine into the config file under `[machines]` (a `[machines.<name>]` table with `ssh` and `taw` when `--taw` is given; a new table at the end when the file has none; a new file when there is none), keeping every comment and line of it; `result.machine` (`name`, `destination`, `taw`), `result.config` and `result.note` (a running app picks the change up within a couple of seconds). A name already listed, a name or destination that `taw config check` would drop, and a config that does not parse are `invalid_argument`, and the file is left as it was |
| `taw machine remove <name>` | `cli:machine:remove` | deletes that machine's line, or its `[machines.<name>]` table, and nothing else; `result.removed`, `result.config` and `result.note`. A name that is not listed is `not_found`, and the file is left as it was |
| `taw image paste --pane <id> [--machine <name>]` | `cli:image:paste` (`image_pasted`: `pane`, `machine`, `path`) | the image on this machine's clipboard into the pane, here or on that machine through its ssh (`result.path` is the file's real path; the path pasted has a backslash before each space it holds); the clipboard tool has 10 seconds to answer, and the popup and the app run each paste as this verb in a process of their own, in a session of their own, which finishes on its own after they have gone (a failure then is shown with `display-message -c` on the client the popup was on, given to the verb as a hidden `--client`; the app outside tmux has none, so none is shown); errors name the cause: no image on the clipboard (`not_found`), no clipboard to read on a Linux machine with neither `WAYLAND_DISPLAY` nor `DISPLAY` set (`not_found`), a clipboard tool that did not answer within 10 seconds (`timeout`), no clipboard tool (`unsupported`), the machine unreachable (`machine_unreachable`), the pane gone (`not_found`), the machine's taw too old to receive (`unsupported`); `taw image paste` and `taw image receive` paste into any pane they are given, a shell's too; only the list limits the paste to an agent's row |

A forwarded verb waits as long as the far command runs, as a local one does: there is no time limit, and `Ctrl-C` ends it. `machine_unreachable` is the error code when no answer came: ssh could not log in or run, no taw is there, or the far taw ended by a signal (ssh reports 255 for it, so the message may be ssh's own last line or `ssh exited 255 without saying why`). Nothing is retried. The far command line is POSIX-quoted and run as `sh -c '<line>' taw <args>`, so a fish or csh login shell changes an argument that holds a backslash.

The feed is `taw machine feed`: protocol 1 is the only one, and `--protocol` names the one the app speaks. Each line is one JSON object with a `type`. The machine sends:

| `type` | Fields |
|---|---|
| `hello` | `taw` (its version), `protocol`, `host`, `server` (`<tmux server pid> <start unix seconds>`, or empty with no server). Always first |
| `state` | `spaces`, `panes`, `agents`, `worktrees`: everything the list draws of that machine, `open_worktrees` (left out when empty): the records of its worktrees one of its sessions runs, which the list never draws and the app uses to name a session's worktree sessions when it asks before closing it, and, beside a folder that sits behind a link there, the folder resolved on the machine (`real_path`, `real_repo_root`), which the app matches by and never draws |
| `toast` | `kind`, `pane` (that machine's id), `text`, `title`, `body`, `agent`, `agent_kind`, `location`, `lease` (the machine saw a fresh lease, so the app that holds it speaks the toast) |
| `ping` | none |
| `left` | `holder`, `pane`, `go`: an attach there ended |

and the app sends `lease` (`holder`, the app's `<host>-<pid>`) and `walk` (`you`, the name the app gives that machine, and `stops`, the walk's ids in the app's own names). Every field is read with a default, so a field a newer taw adds does not stop an older one.

## What a plugin author should expect to work

- `[[build]]`, `[[startup]]`, `[[actions]]`, `[[events]]` (see "Events" above), and
  `[[panes]]` with `placement = "overlay"` (a `display-popup`) or `"side"`/`"bottom"`
  (a `split-window`).
- Calling back into `taw` via `HERDR_BIN_PATH` for any CLI verb, including reading
  the same JSON record shapes (`pane`, `agent`, `workspace`, `tab`, `worktree`)
  herdr's own CLI returns.
- `min_herdr_version` checked against `[plugins] compat_herdr_version` (default
  `"0.9.3"`), the same trust-preview gate (`--yes` or an interactive `y` before any
  `[[build]]`/`[[startup]]` command runs), and the same config/state directory
  layout (`HERDR_PLUGIN_CONFIG_DIR`, `HERDR_PLUGIN_STATE_DIR`).

## What will not work

- Anything that dials `HERDR_SOCKET_PATH` directly instead of going through
  `HERDR_BIN_PATH`.
- Anything that depends on `HERDR_PLUGIN_ACTION_ID` or `HERDR_PLUGIN_ENTRYPOINT_ID` to
  distinguish invocations, rather than reading `HERDR_PLUGIN_EVENT` and
  `HERDR_PLUGIN_CONTEXT_JSON`.
- `[[link_handlers]]`: parsed, never dispatched (see above).
- Kitty graphics, or any other rendering that assumes herdr's own terminal
  renderer rather than a plain tmux pty (herdr removed its `pane.graphics.*`
  methods in 0.9.2).
- `completion_seq` in an agent record: taw's agent records do not carry it
  (`docs/PARITY.md`, "Known divergences").

## Socket methods taw has no verb for

herdr's v0.9.3 socket schema (`third_party/herdr/reference/socket-api-schema.json`, protocol 22) has 102
methods. Most are reachable over argv, with herdr's own field names: each group has its verbs under
`taw <group> --help`. Some are reached under another name: `pane.wait_for_output` is `taw pane wait-output`,
`pane.focus_direction` is `taw pane focus --direction`, `integration.list` is `taw integration status`,
`server.agent_manifests` is `taw manifest list`, `server.reload_config` is `taw config reload`,
`server.reload_agent_manifests` is `taw manifest reload`, `pane.send_input` is `taw pane send-text` and
`send-keys` (`taw pane run` sends text and Enter), and `pane.clear` is taw's own `taw pane clear`, which clears less
(`docs/PARITY.md`, the row of v0.9.2's #4383).

These 21 have no verb:

| Method | Why |
|---|---|
| `events.subscribe`, `events.wait` | a stream needs a live socket: see "Events" above |
| `workspace.move`, `workspace.move_block` | tmux has no session order to set: `docs/PARITY.md`, "Pinned" |
| `ping` | taw has no server to ask |
| `server.stop`, `server.live_handoff` | the server is tmux's: `tmux kill-server` stops it, and tmux has no live handoff to a new binary |
| `server.ssh_agent.register` | keeps a forwarded ssh agent working in herdr's remote panes; not ported |
| `pane.scroll`, `pane.copy_motion`, `pane.copy_search`, `pane.selection.read` | herdr's own copy mode, scroll and selection, driven by a client's viewport and its content revision; tmux's copy mode, scroll and selection are tmux's own |
| `pane.edit_scrollback` | opens the focused pane's scrollback in your editor (herdr's `prefix+e`); not ported: `tmux capture-pane -p -S -` gives the same text to any editor |
| `pane.link.resolve`, `pane.link.activate` | a link under a cell of herdr's renderer: see "Link handlers parse but do not dispatch" above |
| `command.invoke`, `client_shell.surface.set` | herdr's client shell, the surface its own UI draws; there is no such surface in tmux to invoke a command on or hand over |
| `release_notes.dismiss`, `product_announcement.dismiss` | herdr's own update notes and announcements; taw shows neither |
| `pane.clear_agent_authority` | herdr's own CLI has no verb for it either; `taw pane release-agent` is the one that gives up a pane's hook authority, for a named source and agent |
| `tab.move` | tmux's `move-window` and `swap-window` reorder windows; taw has no verb that calls them |
